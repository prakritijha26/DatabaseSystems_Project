# Dry-run and apply implementation

Implement the user's specified APPLY/RESEED workflow in the existing checkout; no Git operations.

1. engine.py: recognize APPLY through the same whitelist, reject prefixed SELECT, fix permitted DROP COLUMN AST handling; commit only after successful execution and telemetry. WHAT_IF/SELECT always roll back. APPLY DDL retains RESTRICT; simulation-only CASCADE previews must never become implicit permanent cascades.
2. engine.py: RESEED/RESET rebuild only the named sample objects using schema.sql and seed.sql in one transaction, since seed.sql alone only inserts and cannot repair dropped columns. Roll back failed reset. Local dedicated demo database only.
3. mock_engine.py/app.py/src/types.ts: extend report with COMMITTED, committed, commit_scope and interlock_message; offline results are explicitly illustrative mock acknowledgements with no real persistence. Preserve no-fallback-on-execution-failure.
4. src/app.ts/web/index.html/src/cli.ts/cli.py: show amber permanent status only for confirmed live commits. Document commands. Prevent automatic HTTP replay of APPLY/RESET after ambiguous request failure.
5. Tests first for lifecycle and validation, then regression suites, browser and CLI checks. Test actual commits only in a disposable local database if available; otherwise report live verification as unavailable.

Contract remains POST /api/whatif with {sql:string}. Existing statuses remain; COMMITTED is additive. Live commit requires committed=true, rolled_back=false, commit_scope=postgresql. Offline COMMITTED has commit_scope=mock and is never presented as a permanent PostgreSQL write. RESET uses statement_type DML, operation RESET and a message. Validation failures remain ERROR. This is sequential dry-run/apply, not prepared/distributed two-phase commit or a guarantee of unchanged state between requests.
